# Contributing to pg-dac

Thanks for helping. Bug reports, ideas, documentation fixes and code are all welcome.

- **Found a bug?** Open an issue with the bug template. The most useful reports include the
  pg-dac version (`pg-dac --version`), the PostgreSQL version of both sides, and a minimal schema
  that reproduces it. Leave out real connection strings and data.
- **Want a feature?** Open an issue to discuss it before writing a large change, so the design
  can be agreed first.
- **Found a security issue?** Don't open an issue; follow [SECURITY.md](SECURITY.md).

By taking part you agree to the [code of conduct](CODE_OF_CONDUCT.md). Contributions are licensed
under the project's [Apache-2.0 license](LICENSE).

## What you need

| For | Install |
|---|---|
| The engine and CLI | Go 1.25+ |
| The desktop app | Node 22 with pnpm 10, and Rust stable. Windows also needs the MSVC build tools; Linux needs `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf` |

No PostgreSQL install is needed: tests and the CLI download a throwaway PostgreSQL the first time
and cache it.

## Repository layout

```
cmd/pg-dac/        the CLI: one file per command group; serve.go is the daemon the desktop app uses
internal/
  model/           the canonical, serializable schema model everything compares
  introspect/      reads the model from a live database (pg_catalog)
  build/ source/   turn a project, a .sql file or an artifact into a model
  devdb/           the throwaway PostgreSQL used to normalize sources and validate migrations
  diff/ plan/      compare two models; order the changes by dependency
  sqlgen/ safety/  render lock-safe SQL; classify each statement's hazards
  engine/          ties the pipeline together; the scenario matrix lives here
  publish/ execute/ deploy/ drift/ refactor/   applying a migration and everything around it
  artifact/ pgbac/ the .pgdac and .pgbac formats
  project/ projsync/  the declarative project, and updating it from a database
  validate/        proves a migration by replaying it in a scratch database
ui/                the Tauri desktop app (React frontend in ui/src, Rust supervisor in ui/src-tauri)
docs/              user documentation; docs/images is generated by `pnpm screenshots`
testdata/          sample projects used by the tests
```

[docs/how-it-works.md](docs/how-it-works.md) explains the pipeline these packages implement.

## Build and test

```bash
go build -o bin/pg-dac ./cmd/pg-dac
go vet ./...
go test -short ./...                 # unit tests, no database
go test -p 1 -timeout 40m ./...      # everything, with embedded PostgreSQL
```

The full suite runs real PostgreSQL instances one package at a time (`-p 1`); the engine's
scenario matrix alone takes several minutes, hence the longer timeout. Scratch servers run
PostgreSQL 16 unless a test names a version; `PGDAC_SCRATCH_MAJOR=13 go test -p 1 ./...` runs the
suite on another major, which is what CI does for every supported one (11 to 18). A fixture or
scenario that needs a newer major than 11 must say so and be skipped below it, not fail. Set
`PG_DAC_TEST_DSN` to a disposable database to also run the self-idempotence check against it.

For the desktop app, from `ui/`:

```bash
pnpm install
pnpm exec tsc --noEmit && pnpm lint && pnpm test
pnpm dev             # the frontend in a browser at http://localhost:1420, with a mock engine
pnpm tauri dev       # the real app; build the sidecar first (ui/README.md)
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

`pnpm dev` needs no database: `src/ipc/mock.ts` replays a recorded plan with the same events and
refusals as the real engine. Use it for UI work and accessibility checks (axe-core from the
browser console). If a change alters what the app looks like, run `pnpm screenshots` to refresh
the README images; it drives the mock with an installed Edge or Chrome.

CI (`.github/workflows/ci.yml`) runs all of the above on every pull request.

## Making a change

1. Fork the repository and create a branch from `main`.
2. Keep the change focused: one fix or feature per pull request.
3. Add a test that fails without your change. Engine changes usually belong in the scenario matrix
   (`internal/engine/scenarios_test.go`) or as a round trip through a real database. Never weaken
   an existing gate to make a change pass.
4. Run `gofmt` and the checks above.
5. Add a line under **Unreleased** in [CHANGELOG.md](CHANGELOG.md) for anything a user would notice.
6. Open a pull request and fill in the template.

Some ground rules the codebase follows:

- **The model is the contract.** Compare models, never SQL text. A false difference is a bug in
  normalization or introspection, not something to filter out at the end.
- **Safe by default.** New statement kinds declare their hazards; anything that can lose data is
  blocked until the user acknowledges it.
- **No secrets in output.** Passwords never appear in arguments, logs, errors or test fixtures.
- **Match SSDT where it makes sense.** When SqlPackage has an equivalent behavior or option, use
  its default and mention the name, so people coming from SQL Server feel at home.

## Releases (maintainers)

1. From `ui/`, run `pnpm release <patch|minor|major|x.y.z>`. It sets the version in every place
   that carries it; `TestVersionsAgree` and the release workflow check they agree.
2. Move the **Unreleased** notes in CHANGELOG.md under the new version and commit as
   `Release vX.Y.Z`.
3. If the change touches the build (`ui/src-tauri`, its dependencies, `.github/workflows/release.yml`),
   do a dry run first: Actions → Release → *Run workflow* on the branch. It builds and signs every
   installer and CLI binary and keeps them as workflow artifacts without creating a release.
4. `git tag vX.Y.Z && git push origin main vX.Y.Z`.
5. The release workflow builds the CLI for five platforms and the desktop installers, signs the
   update files and creates a **draft** release. Check it, then publish it: running apps update
   only from published releases ([docs/UPDATES.md](docs/UPDATES.md)). If a job fails because GitHub
   could not give it a runner (a macOS queue, usually), re-run only the failed jobs; the others
   are kept.
